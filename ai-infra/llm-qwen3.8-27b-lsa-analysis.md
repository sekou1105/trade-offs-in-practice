# LSA 长上下文推理实测：Qwen3.8-27B 在A40显卡上的收益与边界

> 目标：说明 128K 以上长上下文问答的主要成本，拆解Latent Sparse Attention（LSA）的加速原理，并通过Qwen3.8-27B在2×A40上的对比测试，
判断其实际收益。

长上下文模型并不只需要“支持更长的输入”。一个可用的长上下文问答服务，还要同时满足四个条件：**上下文装得下、关键信息找得到、请求时延可接受、并发运行足够稳定。**

LSA 试图解决的是其中的计算与检索效率问题。

---

## 一、128K 以上长上下文问答的难点

### 1.1 上下文窗口不等于有效问答能力

模型支持 128K、256K 甚至更长的上下文，只说明输入长度在结构上有机会被接受，不代表模型能够在整个窗口内稳定检索和使用。

一个长上下文问答请求至少需要完成以下过程：

```text
接收并编码长文档
        ↓
保存历史 token 对应的 KV Cache
        ↓
在大范围上下文中定位与问题相关的内容
        ↓
将相关信息纳入注意力计算
        ↓
生成正确答案，并满足时延和并发要求
```

其中任何一个环节失效，都可能表现为“请求成功返回，但答案不正确”。因此，长上下文测试不能只检查接口是否返回，也不能只测量生成速度，还必须单独验证检索准确率。

### 1.2 全注意力的成本随上下文持续增长

设上下文长度为 `T`。在全注意力中，每个 Query 都需要关注此前所有 Key：

- Prefill 阶段需要处理大量 Query–Key 组合，主要计算成本可近似理解为 `O(T²)`。
- Decode 阶段每生成一个新 token，都需要读取此前的 KV Cache，单步成本随 `T` 增长。
- KV Cache 本身也会随上下文长度和并发数持续增长。

因此，长上下文服务通常同时受到计算、显存容量和显存带宽限制。只增加 GPU 显存，可以解决部分“装不下”的问题，但不会自动消除注意力计算和读取成本。

### 1.3 稀疏注意力仍可能受制于索引器

稀疏注意力的基本思路，是让每个 Query 只关注一部分相关 Key。如果固定选择 `k` 个 Key，注意力本身的计算量会明显下降。

但这里还有一个前置问题：**如何找到这 `k` 个 Key？**

传统 Token Sparse 或 Block Sparse 方法通常需要索引器扫描此前的 Key 或 Block。即使最终参与注意力的 Key 很少，索引过程仍可能随上下文持续增长。在超长上下文下，成本可能从注意力计算转移到“寻找 Key”。

这意味着：

> **减少注意力计算，不等于已经降低整个推理链路的成本。索引、选择、展开和额外内存访问都必须计入端到端时延。**

LSA 正是在这个背景下提出的。

## 二、LSA 的原理及加速原因

### 2.1 核心思路：先找语义簇，再找具体 Key

Latent Sparse Attention 将 Key 映射到学习得到的潜在空间，并按照语义相似性进行聚类。Query 不再直接对全部 Key 逐一评分，而是先检索聚类后的 Bucket，再展开选中的 Bucket 得到具体 Key。[1]

一次 D-LSA 查询可以简化为以下流程：

```text
历史 Key
   ↓
投影与 L2 归一化
   ↓
池化并进行语义聚类
   ↓
保存 Bucket 质心与 Key 位置（Bucket Cache）
   ↓
Query 对 Bucket 质心评分
   ↓
选择 Top-p Bucket 并展开
   ↓
组合长程 Top-k + 局部 Window + Sink
   ↓
只对选中的 Key 执行注意力计算
```

它与按位置切块的稀疏方法有一个重要区别：**LSA 的索引单位是语义簇，而不只是连续 token 块。** 其目标是避免一个关键 token 因为所在块的整体得分不高而被整体跳过。

### 2.2 固定注意力预算为什么能降低 Decode 成本

本次本地 LSA 配置中，每个 Query 默认读取：

| 组成部分 | 数量 | 作用 |
|---|---:|---|
| 长程 Top-k | 4,096 token | 从语义相关的 Bucket 中选择历史信息 |
| 局部 Window | 512 token | 保留最近上下文，并覆盖尚未完成聚类的部分 |
| Sink | 4 token | 保留注意力汇聚所需的特殊位置 |
| 合计上限 | 约 4,612 token | 限制单次查询的注意力范围 |

当上下文从 16K 增长到 128K 时，全注意力需要处理的历史范围显著扩大，而 LSA 实际参与注意力的 Key 数量仍受到固定预算约束。

这解释了后文测试中的一个现象：**LSA 的单请求 Decode 速度在不同输入长度下相对稳定，而 Baseline 会随着上下文变长逐步下降。**

需要注意，固定预算只限制注意力计算范围，并不意味着全部索引成本都变成常数。Bucket 质心搜索、索引展开和缓存读取仍然需要执行。

### 2.3 D-LSA 与 N-LSA 是两条不同路线

论文给出了两种 LSA 形态：

| 形态 | 模型改造方式 | 主要特点 |
|---|---|---|
| D-LSA | 在已有预训练模型上增加索引投影，通过蒸馏学习原模型的注意力选择 | 基础模型冻结，适合改造已有权重 |
| N-LSA | 从训练阶段直接使用下一 token 预测损失学习稀疏选择 | 不需要教师模型和额外索引投影，但需要原生训练 |

本文 A40 测试使用的是 **D-LSA 蒸馏映射**，不是重新训练的 N-LSA 模型。因此，测试结果主要反映“已有模型增加蒸馏稀疏索引器”这条路线。

### 2.4 Flat 与 Tree 不能混为一谈

LSA 的 Bucket 检索包括 Flat 和 Tree 两种思路：

- **Flat**：Query 对全部 Bucket 质心评分，再选择 Top-p。实现直接，但质心扫描成本仍随上下文增长。
- **Tree**：继续对 Bucket 构建层级结构，通过逐层搜索减少需要评分的质心数量，使索引搜索具备亚平方扩展潜力。

Tree 也不是在任何场景下都更快。单请求 Decode 时，层级搜索存在串行开销；当更多请求共同 Decode 时，这部分成本才更容易被摊薄。

因此，“LSA 具有亚平方复杂度”不能直接套用到所有 LSA 配置，必须说明具体使用的是 Flat 还是 Tree，以及测试处于 Prefill 还是 Decode 阶段。

### 2.5 LSA 为什么比原模型更快

与全注意力相比，LSA 的收益来自两部分：

1. **减少注意力计算**：Query 只处理被选中的 Key，而不是全部历史 Key。
2. **降低索引扫描常数**：Query 对压缩后的语义质心评分，而不是直接对每个原始 Key 评分。

但完整成本应按以下方式理解：

```text
LSA 总成本 = 索引投影与聚类
           + Bucket 搜索与展开
           + 选中 Key 的注意力计算
           + KV Cache 与 Bucket Cache 的存储和读取
           + 推理引擎调度及其他模型层开销
```

当上下文较短时，节省的注意力计算可能不足以覆盖新增索引开销；当上下文足够长时，减少的计算和读取才可能转化为端到端收益。

所以，LSA 是否存在收益拐点，以及拐点出现在哪个长度和并发下，必须实测。

### 2.6 论文结果分析

论文在 H200、B300 和 SGLang 环境中评估了最高 10M token 的上下文。在 Qwen3.8-27B 的 10M 测试中，论文报告单个注意力层相对全注意力的 Prefill、Decode 加速分别达到 72.4 倍和 42.5 倍；端到端加速则明显低于单层结果。[1]

这说明两点：

- 单层算子优化可以在超长上下文下产生很大的局部收益。
- 整模型还包含其他层、投影、调度、通信和内存访问，端到端倍率需要单独测量。

论文的硬件、上下文长度、并行方式、内核实现和测试任务均与本文本地环境不同。

**论文结果展示了技术潜力，当前测试用于判断低算力显卡的实际表现，两者不能相互替代。**

## 三、Baseline 与 LSA 版本对比测试

### 3.1 测试环境

本次测试使用相同的 Qwen3.8-27B 基础权重，对比常规全注意力和 D-LSA 服务。

| 项目 | Baseline | LSA |
|---|---|---|
| 注意力方式 | 常规全注意力 | D-LSA 稀疏注意力 |
| 推理引擎 | SGLang 0.5.22 | SGLang fork `lsa-v0.1.0` |
| 权重精度 | BF16 | BF16 |
| GPU | 2×A40，TP2 | 2×A40，TP2|
| KV Cache 容量 | 199,833 token | 163,849 token |
| 主要稀疏参数 | 不适用 | Top-k 4,096、Window 512、Sink 4 |

LSA 的 KV Cache 可用容量比 Baseline 减少约 18%。这与 LSA 需要额外保存索引结构相一致：**LSA 减少的是部分计算和读取，不是删除原始 KV Cache。**


### 3.2 测试方法

准确率测试覆盖 4K、8K、16K、32K、64K 和 128K：

- 每个长度使用 30 条样本。
- 目标信息分别位于文档的 10%、50% 和 90%，每个位置 10 条。
- 问题要求返回文档中唯一的实验验证码。
- 两个版本使用相同输入，`temperature=0`，最多生成 64 token。

性能测试使用相同结构、不同内容的输入，避免 Radix Cache 复用影响结果。主要指标如下：

| 指标 | 含义 |
|---|---|
| TTFT | 从发出请求到收到首个输出 token，包含排队和 Prefill |
| TPOT | 首个 token 之后，平均每生成一个 token 所需时间 |
| Decode | 首个 token 之后的输出速度 |
| 总时延 | 从发出请求到最后一个 token 接收完成 |
| 聚合输出吞吐 | 整个批次所有请求每秒生成的 token 数 |

并发测试覆盖 16K 的 1／2／4／8 并发、32K 的 1／2／4 并发和 64K 的 1／2 并发；128K 仅测试单请求。

另外补充了 12K 输入、400 token 输出的生产场景(作者面对的工作场景)，并发为 1／4／8／16。

### 3.3 单请求性能：明显收益主要出现在 64K 和 128K

以下结果均为单请求、并发 1：

| 输入长度 | 版本 | TTFT Avg（s） | Decode Avg（token/s） | 总时延 Avg（s） |
|---|---|---:|---:|---:|
| 4K | Baseline | 1.182 | 20.33 | 7.48 |
|  | LSA | 1.437 | 19.62 | 7.96 |
| 8K | Baseline | 2.483 | 19.88 | 8.92 |
|  | LSA | 3.040 | 19.57 | 9.58 |
| 16K | Baseline | 5.395 | 19.04 | 12.12 |
|  | LSA | 6.263 | 19.57 | 12.80 |
| 32K | Baseline | 12.449 | 17.55 | 19.74 |
|  | LSA | 12.894 | 19.58 | 19.43 |
| 64K | Baseline | 31.701 | 15.15 | 40.15 |
|  | LSA | 26.559 | 19.55 | 33.11 |
| 128K | Baseline | 90.331 | 11.93 | 101.06 |
|  | LSA | 55.065 | 19.53 | 61.62 |

从数据可以看到三个层次。

**短上下文没有体现收益。** 4K～16K 下，LSA 的 TTFT 和总时延均高于 Baseline，说明新增索引流程的固定开销尚未被节省的注意力计算覆盖。

**32K 附近开始接近，64K 后出现明显收益。** 32K 下两者总时延接近；64K 下，LSA 的 TTFT 降低约 16.2%，总时延降低约 17.5%。

**128K 的收益最明确。** LSA 将 TTFT 从 90.331 秒降至 55.065 秒，降低 39.04%；总时延从 101.06 秒降至 61.62 秒，降低约 39.03%；Decode 速度提高约 63.64%。

另一个值得关注的现象是 Decode 的稳定性：Baseline 从 4K 的 20.33 token/s 降至 128K 的 11.93 token/s，而 LSA 在各长度下基本维持在 19.5 token/s 左右。
这与固定注意力预算的设计相符。

### 3.4 并发与生产场景

部分并发结果如下：

| 场景 | 版本 | 聚合输出（token/s） | 请求吞吐（req/s） | 总时延 Avg（s） |
|---|---|---:|---:|---:|
| 16K，8 并发 | Baseline | 20.35 | 0.159 | 50.19 |
|  | LSA | 17.95 | 0.140 | 56.92 |
| 32K，4 并发 | Baseline | 8.92 | 0.070 | 57.25 |
|  | LSA | 8.77 | 0.068 | 58.26 |
| 64K，2 并发 | Baseline | 3.55 | 0.028 | 71.87 |
|  | LSA | 4.28 | 0.033 | 59.73 |

16K、8 并发时，LSA 的聚合输出吞吐下降 11.79%，总时延也有所增加；32K、4 并发时两者基本接近；64K、2 并发时，LSA 的吞吐和时延开始体现优势。

在更接近生产负载的 12K 输入、400 token 输出场景中，并发 1／4／8／16 的实测结果均为 LSA 稍慢，差距约 10%。

这说明长上下文单请求的收益，不能简单解释为所有生产流量都会受益。

并发调度、输出长度、索引开销和批处理效率都会改变最终结果。评估时应使用真实输入长度、输出长度和并发分布，而不是只选择最有利的测试点。

### 3.5 准确率

| 输入长度 | Baseline 准确率 | LSA 准确率 |
|---|---:|---:|
| 4K | 100.00% | 100.00% |
| 8K | 90.00% | 93.33% |
| 16K | 23.33% | 10.00% |
| 32K | 6.67% | 0.00% |
| 64K | 0.00% | 0.00% |
| 128K | 0.00% | 0.00% |

两个版本在 4K 下均能正确完成任务，但从 16K 开始准确率快速下降，64K 和 128K 均为 0。

这组结果需要谨慎解读：

- 它不能证明 LSA 在长上下文下保持了检索质量。
- 它也不能把全部问题归因于 LSA，因为 Baseline 同样出现了严重下降。
- 在准确率异常未定位前，128K 的性能提升只能视为速度结果，不能视为完整问答能力通过验收。

后续应优先检查样本与判分链路、模型原始输出、实际 Prompt 长度、上下文与位置编码配置，以及 D-LSA 映射和稀疏参数是否正确生效，并使用论文中的 RULER 等任务进行对照。

### 3.6 当前测试能够说明什么

本次测试能够说明：

- 当前两套 A40 服务配置在若干长度和并发下的实际性能差异。
- **LSA 在 64K、128K 单请求下存在明显收益**。
- LSA 在短上下文和部分并发场景下可能引入额外开销。

本次测试不能直接说明：

- LSA 在所有模型、GPU 和推理引擎上都具有相同收益。
- 单请求的结果可以代表高并发服务能力。

## 四、结论

### 4.1 核心结论

LSA 的价值不是简单地“让模型支持更长上下文”，而是通过语义索引和固定注意力预算，降低长上下文下寻找和使用历史信息的成本。
在本文的 Qwen3.8-27B 测试中，可以得到以下结论：

1. **128K 单请求收益明确**：TTFT 降低 39.04%，总时延降低约 39.03%，Decode 速度提高约 63.64%。
2. **收益具有长度和并发边界**：短上下文没有体现收益，16K 高并发和 12K 生产场景还出现了性能回退。
3. **资源开销不能忽略**：原始 KV Cache 仍需保留，索引结构还会占用额外资源，本地 KV Cache 可用容量减少约 18%。
4. **准确率问题**：本轮 64K、128K 测试中两个版本准确率均为 0，需要重新评估准确率方案。

### 4.2 适用场景判断

针对不同的业务场景，该方案的适用性存在差异，具体判断如下：
对于 **64K～128K** 低并发、长输入问答 场景，鉴于 TTFT、总时延和 Decode 阶段均已体现出收益，该场景值得进一步验证。
然而，对于 **4K～16K** 的短请求 场景，由于固定的索引开销可能会导致服务变慢，因此不建议默认替换 Baseline。


总体而言，**LSA 在本次 A40 测试中展现了明确的长上下文性能潜力，但这种潜力具有场景边界。128K 单请求的 39% TTFT 降幅值得继续关注，
短请求和并发场景则需要单独评估。**
